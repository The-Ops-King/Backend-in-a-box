# Code audit, 2026-10-19

Tyler: "a full code audit to see where we're overcomplicating things, what our potential issues are, where there is any dead
code, and ... where something's hard-coded when it shouldn't be ... all that the code does really is run the workflow."
Read-only, five passes over `platform/` at 3e79bff (after the onboarding merge). Paths are under `platform/`. Findings are as
reported; anything marked (S) was suspected, not proven in code.

## 1. Risks (most severe first)

1. **Critical: preview builds migrate the production database.** `package.json` runs `scripts/migrate.ts` on every build;
   previews share the production database (TODO.md "Decide: give previews their own database"). A branch's unreviewed
   migration runs against production, with no transaction or lock, and stale branches drop and re-add old check constraints
   (`src/db/migrate.ts` 46-58, 66, 86-90, 233). Fix: migrate only when `VERCEL_ENV=production`; one transaction with an
   advisory lock; numbered migrations instead of re-running DDL on every deploy.
2. **High: a text can go out twice.** A run is one transaction (`runner.ts:91`); the `sends` row, the vendor call and the row
   update are inside it (`executor.ts` ~161-179). A function kill (300s), a later SQL error, or a 5xx after GHL accepted rolls
   the row back or marks it `failed`, and the retry sends again. `ghl()` has no timeout; the daily sweep ticks every company
   serially in one function. Fix: commit the queued row before the vendor call (open item 23); an "unknown" status reconciled
   by delivery status, not retried blind; fetch timeouts; a time budget per tick.
3. **High: the Slack bot's SQL tool can read other clients' rows.** Tables without `company_id` have no tenant policy
   (`companies`, `run_steps`, `workflow_versions`, `workflow_templates`, `engine_state`, `playbook_releases`) and the query role
   can read them (`query.ts:57`). `run_steps.result` holds other clients' would-send copy and contact ids. Any member of a
   client's Slack can ask. Fix: deny those tables (or give `run_steps` a `company_id`), limit the tool to owners/managers.
4. **High: quiet mode writes GHL for real, and the client's own GHL automations can text from it.** Tags, stages and fields
   are written in quiet (only ghost holds them); the send lock never sees GHL's own sends. Fix: an inventory of the GHL
   workflows triggered by what the engine writes, as a readiness blocker before quiet or live.
5. **Medium-high: an unlocked workflow stays unlocked through later edits** (`sends_unlocked_at` survives new versions). Fix:
   keep the unlocked version; relock when a send or webhook step is added or changed.
6. Medium: the dashboard is one shared password with no per-client scope (`middleware.ts`); open item 22 is out of date.
7. Medium: row-level security is mostly bypassed (152 `asOperator` vs 6 `asCompany`); isolation rests on hand-written
   `where company_id`. Check the login role's BYPASSRLS (S).
8. Medium: every deploy re-validates `events_source_check` under an exclusive lock, and drops and re-adds the appointments and
   payments unique constraints (a duplicate in the gap leaves dedupe off); `drop table metrics_daily/report_schedules` runs on a
   shared database.
9. Medium: the operator key sits in plaintext in pg_cron (`schedule.ts:18`); `/api/tick` is open when `CRON_SECRET` is unset.
10. Medium: replay with `again` starts new runs whose sends have new idempotency keys (`replay.ts:31`).
11. Medium: the inbound poll reads only the 50 newest conversations a tick (`ghl/read.ts:55`): at volume a reply is missed and a
    follow-up goes to someone who answered.
12. Medium: the scheduler and watchdog both live in the database (pg_cron); nothing outside pages if it stalls.
13. Low: public `/api/health` lists every client slug; retention deletes `sends` rows of paused runs (a later retry re-sends);
    Zapier secret compared non-constant-time; Zapier payment door treats an unknown status as succeeded; webhook URLs with a
    token in the path are stored in `run_steps`; an invalid contact time zone fails the run (S).

Sound: webhook signatures (Whop, Fathom, Slack, Typeform) per company and constant-time; Slack buttons check the presser's
role; the send lock checks the live CRM contact; every text and email goes through `executor.ts doSend`.

## 3. Overcomplicated

1. Settings read by hand ~70 times in ~35 files, with booleans parsed four different ways. One registry
   `{key: {kind, default}}` and one `setting(b, key)` (this is also part 2 of open item 50).
2. Every step type is a `case` in six files (executor, describe, words, blocking, example, coverage, step-docs), with two
   different `kindOf`. One file per step type exporting `{schema, run, describe, blocking, docs}`.
3. The same CRM-write guard (ghost → would; no CRM id → fail; claim; vendor call; done) hand-written in seven steps, and the
   send guard (held → lock → claim) in three: two helpers, where a mode or lock bug can no longer hide.
4. `notify_owner` re-implements `slack_post` (one template uses it); the Slack token query is written 15+ times.
5. The pinned-deadline logic five times; ~20 hand-written `{{path}}` regexes that disagree.
6. Four ways to inject a vendor (`Adapters`, `HealthProbes`, `GhlReads`, `TypeformApi`); raw Slack and Calendly calls outside
   adapters.
7. Health sweep is one 270-line function; `tick()` one 240-line loop.
8. Contact lookup written ~8 times; phone normalisers disagree (`poll.ts:21` vs `send-lock.ts:16`); `normEmail` three times.
9. Unused or misleading step options: `pause_runs.scope` ignored, `start_workflow.with` never reaches the run, `branch.on`
   never read. Three tag step types (`tags`, `set_tag`, `remove_tag`).
10. Compatibility layers that a one-time data migration could retire (pre-D88 eod text, "shadow", `LEGACY_LOCK`, old-row
    special cases); `migrate.ts` re-runs ~300 lines on every deploy.

## 5. Vendor coupling (for swapping tools later)

| Vendor | Swappable today | Main blocker |
|---|---|---|
| GHL (CRM, texts) | hard | `ghl_*` columns in 8 tables; GHL URLs in ~12 templates; `GhlReads` bypasses the adapter (metrics, reports, bot); opportunities / custom objects in the step types; sends take a CRM contact id |
| Slack | hard | `slack_post` 44 times in templates; Slack mention and link markup in templates; executor reads `slack_connections` directly; Block Kit, emoji reactions in the interface |
| Calendly | medium-easy | closed `"ghl" \| "calendly"` union; health and install call it directly |
| Whop | medium | direct imports in 6 places; `whop_*` columns. Commas can come in through the Zapier payment door today |
| Typeform | medium | no form-source interface; its door writes GHL |
| Fathom | easy-medium | `meetings()` returns Fathom's objects |
| Zapier, Anthropic / Jev | easy | already neutral |

Target shape: each vendor a port with a registry by provider name (`Crm`, `CrmMetrics`, `Scheduler`, `Messenger`, `Notifier`,
`PaymentSource`, `Recorder`, `FormSource`, AI), each with `health()` and `install()`; company config names its providers;
neutral steps (`notify` for `slack_post`, `deal` for `pipeline_card`, `wait_for_ack` for `wait_for_reaction`); templates use
`{{mention}}`, `{{link}}` and `{{contact.crm_url}}`, never vendor markup or URLs; columns renamed to `crm_*` / `provider_*`.
Then "speed to lead from HubSpot to Discord" is two adapters and two settings, no workflow changes.
